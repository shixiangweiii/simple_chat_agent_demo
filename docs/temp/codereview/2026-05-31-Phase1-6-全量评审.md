## 详细发现

### 1.【高】置信度尾缓冲拖垮短答案的流式体验

**位置**:`chat_core.py:872-878`(`_buffer_confidence_delta`)、被 `_stream_react_rounds:1497` 与 `stream_agent_response:2367` 调用。

```python
def _buffer_confidence_delta(tail: str, delta: str) -> tuple[str, str]:
    tail += delta
    if len(tail) <= CONFIDENCE_TAIL_CHARS:   # 240
        return tail, ""                       # ← 累计未超 240,什么都不发
    emit = tail[:-CONFIDENCE_TAIL_CHARS]
    return tail[-CONFIDENCE_TAIL_CHARS:], emit
```

为了在结尾剥掉 `[confidence: ...]` marker,流式过程中**始终扣留最后 240 字**。后果:

- 答案总长 ≤ 240 字时,**流式阶段一个字都不发**,全部堆到 `_finalize_confident_answer` 末尾一次性 `("chunk", remainder)` 吐出。
- 答案 > 240 字时,**最后 240 字**也是末尾一次性蹦出。

`USER_PROMPT` 明确要求"回复简洁明了"(`chat_core.py:239`),被鼓励的正是短答案 —— 也就是**最常见路径**。而且 `TOOLS == []` 恒成立,responses 模式 `has_tools` 恒为 False(`stream_agent_response:2327`),所以 responses / chat **两条默认路径的短答案全都不再逐字流式**,用户体验从"打字机"退化为"思考中…→ 整段蹦出"。这是 Phase 6 引入的回归。

**失败场景**:用户问"今天星期几",模型答"今天是周六。[confidence: 0.9 | reason: ...]"(<240 字)→ 思考面板折叠后答复区长时间空白,然后整句突然出现。

**建议**:不要无条件扣留固定尾窗。可改为"仅当尾部疑似出现 marker 起始符时才进入缓冲":检测到行尾 `[` 或 `[confidence` 前缀才扣留,否则正常逐字发;或流式照常发、在 finalize 时用 `_CONFIDENCE_MARKER_RE` 从已渲染文本里删掉 marker(前端 `appendAnswer` 已是全量重渲染 `answerBuf`,finalize 时把 buf 末尾 marker 截掉再重渲染一次即可),既不泄漏又不牺牲流式。

### 2.【中】`plan_decision="update"` 重置已完成步骤状态且不重跑

**位置**:`chat_core.py:2037-2040`(plan_decision update 分支)、`_normalize_plan_steps:1005`。

```python
# _normalize_plan_steps
"status": step.get("status") if step.get("status") in {"done", "skipped"} else "pending",
```

```python
# plan_decision_response, decision == "update"
plan["steps"] = _normalize_plan_steps(steps or plan["steps"])  # steps 来自前端
```

前端 `collectPlanSteps`(`index.html:2387-2396`)只回传 `{id, title}`,**没有 status 字段**。于是 `_normalize_plan_steps` 把每一步 status 都判成 `pending`,**包括之前已 `done` 的步骤**。随后 `_plan_decision_inner` 用 `start = step_index`(失败步索引)调 `_execute_plan_steps`,循环从失败步开始 —— 失败步之前那些被重置成 `pending` 的已完成步**既不会被重新执行**(循环起点在它们之后),**也不再显示为 done**。

**失败场景**:3 步计划,步骤 1、2 成功,步骤 3 失败,用户点"修改后继续"→ 步骤 1、2 在卡片上变回 `○ pending` 且永不再跑,最终完成摘要把它们记成 pending。状态前后不一致。

**建议**:`update` 分支只重置目标失败步,保留其余步骤已有 status;或前端回传时带上现有 status 让 `_normalize_plan_steps` 透传(已支持 done/skipped 透传)。

### 3.【中】长 reason 时 confidence marker 泄漏进正文

**位置**:`chat_core.py:849-852`(`_CONFIDENCE_MARKER_RE`)、`_extract_confidence_signal:881`。

```python
_CONFIDENCE_MARKER_RE = re.compile(
    r"\s*\[\s*confidence\s*:\s*(?P<score>...)\s*"
    r"(?:\|\s*reason\s*:\s*(?P<reason>[^\]]{0,120}))?\]\s*$",  # reason 上限 120
    ...)
```

两道阈值耦合出一个洞:reason 捕获上限 **120 字**,尾缓冲窗 **240 字**。当模型输出的 reason 超过约 120 字、整段 marker 超过 240 字时:

- 正则匹配失败(`[^\]]{0,120}` 之后还没遇到 `]`),`_extract_confidence_signal` 当作无 marker → 整段(含 `[confidence: ...]` 字面量)被当成 clean_text;
- 同时 `_buffer_confidence_delta` 早已把 marker 前缀作为正文 emit 出去了。

结果:用户在答复里看到生的 `[confidence: 0.8 | reason: 一长串原因]`,且置信度回落到默认 0.7。

**失败场景**:模型对一个复杂问题给出详尽的 reason(很常见,因为 prompt 没限制 reason 长度)。

**建议**:reason 正则上限放宽并与 `CONFIDENCE_TAIL_CHARS` 对齐(或干脆 `[^\]]*`),并在 prompt 里约束 reason 长度;配合发现 #1 改造缓冲策略后此问题一并消失。

### 4.【中】"修改后继续"是误导性死交互

**位置**:`index.html:2555-2593`(`addPlanDecisionBubble`)、对照 `renderPlanCard` 的可编辑分支(`2417-2450`)。

计划失败决策气泡提供"跳过 / 重试 / 修改后继续"三个按钮,但气泡本身**只有一段错误文字**,没有任何步骤编辑器。点"修改后继续"时执行:

```js
steps: decision === 'update' ? collectPlanSteps(PLAN_CARDS.get(payload.plan_id)) : null,
```

而此时 plan 卡早已被确认时 `renderPlanCard(card, data, false)` 冻结(input disabled、无新增行、无上下移)。所以"修改"无从修改,`collectPlanSteps` 只是把当前冻结的标题原样回传。叠加发现 #2,这个按钮实际效果 = 重置状态后的"重试",与命名承诺不符。

**建议**:要么在决策气泡里渲染一个可编辑步骤列表(复用 `buildPlanStepRow(step, true)`),要么去掉"修改后继续"按钮。

### 5.【中】非 HITL 边界中断的计划无法恢复,Phase 5 承诺打折

**位置**:`chat_core.py:1922-1980`(`_execute_plan_steps`,中途把 `plan["status"]="running"` 并落盘)、`runtime_state_snapshot:504` / `_plan_runtime_snapshot:490`。

可被恢复并继续执行的计划只有两类入口:
- `pending_confirmation` → `/api/plan_confirm`;
- `paused`(步骤失败或步骤级 HITL)→ `/api/plan_decision` 或 `/api/resume`。

但如果进程在**某步的 LLM 调用过程中**(非 HITL 边界)被杀,该 plan 落盘时 status 是 `running`。重启后 `_plan_runtime_snapshot` 给出 `editable=false, decision_required=false`,前端 `upsertPlanCard` 把它渲染成一张"运行中"的卡 —— **没有任何按钮、没有任何入口能让它继续**。计划就此卡死。

**失败场景**:执行 3 步计划,跑到第 2 步搜索时重启服务 → 用户回来看到计划停在"步骤 2 ● 运行中",再无办法推进。

**建议**:恢复时把 `running` 视作可恢复态,给前端一个"继续执行"入口(调用 `_execute_plan_steps(start=current_step_index)`),或恢复时把未完成的 `running` 步骤降级为 `pending` 并暴露继续按钮。

### 6.【低】已完成计划永不回收

**位置**:`chat_core.py:1971`(`_execute_plan_steps` 末尾 `plan["status"]="done"` 后仍留在 `_PLANS`)。

计划完成只改 status、写一条 Memory 摘要,**不从 `_PLANS` 删除**,因此也一直留在 sidecar JSON 里。每次 `loadRuntimeState` 都会把所有历史 done 计划重新 `upsertPlanCard` 渲染一遍,sidecar 随会话内计划数单调增长。

**建议**:完成后从 `_PLANS` 移除(或保留状态但 `runtime_state_snapshot` 过滤掉 `status=="done"` 的计划不下发)。

---

### 7.【低】多入口流式无并发互斥

**位置**:`index.html` 的 `sendUiAction:2299` / `consumePlanConfirmStream:2513` / `consumePlanDecisionStream:2534` / `consumeResumeStream:2743`。

只有 `send()` 检查 `$send.disabled`(`2270`)。其余四个流入口都直接 `setStreaming(true)` 但**不检查当前是否已有流在跑**。快速连点(如计划卡上两个按钮、或 UI 卡上两个 button)会并发发起两条 SSE 流,后端这两条流会并发改同一 session 的 `Memory` / `messages` / `_UI_SURFACES` / `_PLANS`(均无锁)。

**失败场景**:声明式 UI 上有两个 action 按钮,用户快速各点一次 → 两条 `/api/ui_action` 流交错追加 `role=tool` 消息到同一个 messages 列表,可能造成 tool_call_id 配对错乱、模型 400 或答案串台。教学 demo 中概率低,但属真实数据竞争。

**建议**:所有流入口统一在开头 `if ($send.disabled) return;` 复用 `setStreaming` 的互斥语义。

---

### 8.【低】结构损坏的 sidecar 可在恢复时崩溃

**位置**:`chat_core.py:476-487`(`_restore_runtime_state` 的 surface/plan 恢复段没有 try 包裹)、`_extract_ui_actions:1170-1186`(`actions[comp["id"]]` 直接下标)。

`_restore_runtime_state` 只在 `json.loads` 外层有 try(`463-467`)。若 sidecar 是合法 JSON 但内部结构异常(例如某 button 组件缺 `id`,而 `actions` 字段恰好不是 dict 触发 `481` 的重算分支),`_extract_ui_actions` 的 `comp["id"]` 会抛 `KeyError`,沿 `get_or_load` / `read_history` / `/api/chat` 一路冒泡成 500。文档(及 Phase 5 描述)承诺"损坏或版本不兼容的 sidecar 记录 warning 并忽略"。

注:正常落盘的 surface 都带已校验的 `id` 和 `actions` dict(重算分支因此被跳过),所以触发需要手改文件或旧版本遗留 —— 概率低,但与健壮性承诺相悖。

**建议**:把 surface/plan 恢复段也纳入 try,任一结构异常就丢弃该 session 的 runtime state(与"损坏即忽略"语义一致)。
