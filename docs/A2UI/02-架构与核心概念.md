# 02 — 架构与核心概念

## 2.1 三层架构

A2UI 采用三层解耦架构，每层职责单一：

```
┌─────────────────────────────────────────────────────────┐
│                   Agent (服务端)                          │
│  生成 A2UI JSON 消息 → 描述 "UI 应该长什么样"              │
└────────────────────────┬────────────────────────────────┘
                         │ JSONL / SSE / WebSocket / A2A / AG-UI
                         ▼
┌─────────────────────────────────────────────────────────┐
│  Layer 1: UI Structure (surfaceUpdate / updateComponents)│
│  定义组件结构、属性、ID 引用、层级关系                       │
├─────────────────────────────────────────────────────────┤
│  Layer 2: Application State (dataModelUpdate)            │
│  管理数据模型，通过 JSON Pointer 绑定 UI 与状态              │
├─────────────────────────────────────────────────────────┤
│  Layer 3: Client Rendering (原生组件映射)                  │
│  客户端根据组件类型 → 映射到原生框架组件 → 渲染像素            │
└─────────────────────────────────────────────────────────┘
```

**核心设计原则**：

1. **生成-渲染解耦** (Generation-Rendering Decoupling)：Agent 生成"意图蓝图" (JSON)，客户端用本地组件渲染。Agent 永远不执行代码。
2. **数据-结构分离** (Data-Structure Separation)：UI 结构（组件树）与应用状态（数据模型）独立更新，互不干扰。
3. **流式渐进渲染** (Streaming Progressive Rendering)：消息以 JSONL 流式传输，组件到达即可渲染，无需等待完整响应。

## 2.2 核心抽象

### Surface（画布/容器）

Surface 是 A2UI 的顶级 UI 画布概念：

- 每个 Surface 有唯一 `surfaceId`（如 `"booking"`、`"search-results"`）
- 一个 Surface 包含一组扁平组件列表
- Surface 有生命周期：创建 → 渲染 → 交互 → 销毁
- 一个 Agent 会话可管理多个 Surface

```
Session
├── Surface "booking"     ← 餐厅预订表单
│   ├── Component "title" (Text)
│   ├── Component "date"  (DateTimeInput)
│   └── Component "submit" (Button)
├── Surface "results"     ← 搜索结果卡片
│   ├── Component "card-1" (Card)
│   └── Component "card-2" (Card)
└── Surface "map"         ← 地图展示
    └── Component "map-view" (Image)
```

### Component（组件）

组件是 UI 的原子单元，使用**邻接表模型**（见 [04-组件模型与数据绑定](04-组件模型与数据绑定.md)）：

- 每个组件有唯一 `id`
- 组件类型来自 Catalog（白名单）
- 组件通过 `children` 字段引用子组件 ID
- 属性支持字面值和数据绑定

### Catalog（组件目录/注册表）

Catalog 定义了 Agent 可用的组件及其属性/事件/渲染器：

- 客户端在启动时注册 Catalog（组件白名单）
- Agent 只能请求 Catalog 中已声明的组件
- Catalog 是 A2UI 安全模型的核心：从源头杜绝代码注入
- v0.9 引入 `catalogId` 支持外部 Catalog 引用

### DataModel（数据模型）

DataModel 是 Surface 的交互数据层：

- 与 UI 结构独立，通过 JSON Pointer 路径绑定
- 支持响应式更新：数据变化 → UI 自动重渲染
- v0.9 新增双向同步：用户交互可更新 DataModel 并同步回 Agent

## 2.3 端到端数据流

以餐厅预订为例：

```
1. 用户输入："订明天19:00两人桌"

2. Agent 理解意图，生成 A2UI 消息序列：
   → createSurface { surfaceId: "booking", catalogId: "restaurant" }
   → updateComponents { surfaceId: "booking", components: [
       { id: "title", component: "Text", text: { literalString: "预订餐厅" } },
       { id: "date", component: "DateTimeInput", value: { path: "/booking/date" } },
       { id: "guests", component: "TextField", label: "人数", value: { path: "/booking/guests" } },
       { id: "submit", component: "Button", child: "submit-text", action: { name: "confirm" } }
     ]}
   → updateDataModel { surfaceId: "booking", updates: [
       { path: "/booking/date", value: "2026-06-10T19:00" },
       { path: "/booking/guests", value: "2" }
     ]}

3. 传输层：JSONL 消息流通过 SSE/WebSocket/A2A 发送到客户端

4. 客户端解析 JSON，映射为原生组件，渐进式渲染：
   React → <Text><DateTimeInput><TextField><Button>
   Flutter → Text() / DateTimeInput() / TextField() / ElevatedButton()

5. 用户交互（选日期、改人数、点提交）
   → 客户端封装操作事件发回 Agent
   → v0.9: 用户交互自动同步 DataModel 回 Agent

6. Agent 处理事件，生成新 A2UI 消息更新界面
```

## 2.4 与本项目架构的对照

| A2UI 概念 | 本项目对应 | 差异 |
|---|---|---|
| Surface | `_UI_SURFACES[sid]` | 同构；本项目 Surface 含扁平组件树 + data |
| Component | `DeclarativeRenderer` 组件 | A2UI 组件属性更丰富（数据绑定、usageHint 变体） |
| Catalog | 无（硬编码 `text/card/row/column/table/button`） | A2UI 有动态白名单；本项目组件集固定 |
| DataModel | `_UI_SURFACES[sid].data` + `ui_data_update` | A2UI 用 JSON Pointer 精细绑定；本项目用根替换 / 路径写入 |
| Surface 状态机 | 无（无 `createSurface` 生命周期） | 本项目直接 `ui_surface_create` |
| 双向数据同步 | 单向（`/api/ui_action` 手动触发） | v0.9 支持自动同步 |

本项目 Phase 3 的声明式 UI 实现与 A2UI 核心概念高度同构，但更轻量：
- 无 Catalog 安全模型（组件集硬编码）
- 无 JSON Pointer 数据绑定（用简化路径写入）
- 无 Surface 生命周期状态机
- 无双向数据同步
