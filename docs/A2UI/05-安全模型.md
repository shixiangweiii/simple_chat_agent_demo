# 05 — 安全模型

## 5.1 设计哲学

A2UI 的安全模型核心理念：**"像数据一样安全，但像代码一样富有表现力"**

传统 Agent UI 方案的安全困境：
- **LLM 生成 HTML/JS**：XSS 风险高，沙箱隔离但体验差
- **LLM 生成代码执行**：RCE 风险，信任边界模糊
- **MCP Apps (ui://)**：iframe 沙箱隔离，但丧失原生体验

A2UI 的解法：**只传输声明式数据，不传输可执行代码**。Agent 无法注入脚本、HTML 或任意代码。

## 5.2 声明式安全

### 核心原则

1. **数据 ≠ 代码**：A2UI 消息是纯数据（JSON），不是程序
2. **渲染权在客户端**：Agent 只能描述"要什么 UI"，客户端决定"怎么渲染"
3. **组件白名单**：Agent 只能使用 Catalog 中预注册的组件
4. **属性验证**：组件属性必须符合 Catalog 中定义的 schema

### 对比传统方案

| 方案 | 安全模型 | 攻击面 | 风险 |
|---|---|---|---|
| LLM 输出 HTML | 信任 LLM 输出 | XSS, CSRF, 点击劫持 | 高 |
| iframe 沙箱 | 进程隔离 | 沙箱逃逸, 通信劫持 | 中 |
| A2UI 声明式 | 数据白名单 | 组件属性滥用 | 低 |

## 5.3 基于目录的信任 (Catalog-based Trust)

Catalog 是 A2UI 安全模型的核心机制：

```
┌──────────────────────────────────────────┐
│                Agent                      │
│  只能请求 Catalog 中已注册的组件             │
│  组件属性必须符合 Catalog 定义的 schema     │
└──────────────────┬───────────────────────┘
                   │ A2UI JSON 消息
                   ▼
┌──────────────────────────────────────────┐
│             Catalog (白名单)              │
│  ├── Text    { text: StringBinding }     │
│  ├── Button  { child: string, action }   │
│  ├── Card    { children: string[] }      │
│  └── ProductCard { ... } ← 自定义组件    │
└──────────────────┬───────────────────────┘
                   │ 验证通过 → 渲染
                   │ 验证失败 → 拒绝
                   ▼
┌──────────────────────────────────────────┐
│           Client Renderer                 │
│  用原生组件渲染，继承宿主样式和无障碍特性     │
└──────────────────────────────────────────┘
```

**Catalog 的安全属性**：

1. **组件白名单**：Agent 请求未注册组件 → 客户端拒绝渲染
2. **属性约束**：Agent 传了 Catalog 未定义的属性 → 客户端忽略
3. **事件约束**：Agent 注册的 Action 才能触发 → 客户端只处理白名单内事件
4. **类型安全**：属性值必须符合 schema 定义的类型

## 5.4 双重验证 (Dual Validation)

来自 B站 Vue 渲染器的生产实践，A2UI 推荐双层验证：

### 第一层：结构验证 (Structural Validation)

验证消息格式和组件合法性：

- 消息类型是否合法（`createSurface` / `updateComponents` / ...）
- 组件是否在 Catalog 白名单中
- 组件属性是否完整且类型正确
- Action 名称是否在白名单中

### 第二层：过渡验证 (Transition Validation)

验证 Surface 状态机一致性：

```
Not Created ──createSurface──→ Created ──updateComponents──→ Interactive
                                                              │
                          deleteSurface ←──任意状态────────────┘
```

验证规则：
- 不能更新未创建的 Surface
- 同一 Surface 不能重复 `createSurface`
- `updateComponents` / `updateDataModel` 的 `surfaceId` 必须匹配已创建的 Surface

## 5.5 Smart Wrapper 模式

Google 推荐的 Catalog 注册模式——"Smart Wrapper"：

```python
# 服务端注册 Catalog
catalog = Catalog("restaurant-catalog")
catalog.register("ReservationCard", properties={
    "restaurant": { "type": "string" },
    "date": { "type": "StringBinding" },
    "guests": { "type": "NumberBinding" },
    "onConfirm": { "type": "Action" }
})
```

```typescript
// 客户端注册渲染器
renderer.register("ReservationCard", ({ restaurant, date, guests, onConfirm }) => (
  <ReservationCard
    restaurant={restaurant}
    date={date}
    guests={guests}
    onConfirm={() => handleAction(onConfirm)}
  />
))
```

**安全保障**：
- Agent 只能说"给我一个 ReservationCard"，不能控制渲染细节
- 客户端渲染器可以用 DOMPurify 清洗文本、用 CSS 控制样式
- 即使 Agent 恶意输入，也只是在白名单组件的属性范围内

## 5.6 与 MCP Apps 安全模型对比

| 维度 | A2UI | MCP Apps (ui://) |
|---|---|---|
| 信任模型 | 信任组件目录，不信任 Agent 内容 | 不信任 Agent 内容，沙箱隔离 |
| 隔离方式 | 白名单组件 + 属性验证 | iframe sandbox |
| 代码执行 | 无（纯声明式数据） | Agent 输出完整 HTML/JS |
| 样式继承 | 继承宿主应用样式（原生体验） | iframe 内独立样式 |
| 跨平台 | 原生组件渲染 | 仅 Web |
| 安全漏洞率 | 声明式设计显著降低（社区引用数据：降低 73%） | 依赖 iframe 沙箱实现 |

## 5.7 与本项目安全模型的对照

| A2UI | 本项目 | 差异 |
|---|---|---|
| Catalog 组件白名单 | 硬编码 6 种组件 | A2UI 动态白名单；本项目固定 |
| 属性 schema 验证 | 无（信任 Agent 输出） | A2UI 有类型约束；本项目信任 LLM |
| Surface 状态机 | 无 | A2UI 有生命周期验证 |
| 文本渲染：textContent | textContent | **一致**：两者都用 textContent 防 XSS |
| Action 事件白名单 | `/api/ui_action` 验证 registry 中保存的 action context | 同构；A2UI 更系统化 |
| 自定义组件 | 无 | A2UI 支持业务级自定义组件 |

本项目 Phase 3 的安全实践与 A2UI 理念一致（textContent、不执行 HTML/JS），但缺少 Catalog 白名单和 Surface 状态机验证。
